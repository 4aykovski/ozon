# Ozon service

Сервис для интеграции MarketVision с маркетплейсом Ozon. Он владеет Ozon-
спецификой, получает данные через Ozon Seller API и хранит полные raw-данные,
не выполняя расчёты отчётов самостоятельно.

## Архитектура

Описание ниже синхронизировано с документами команды Development в Linear:

- [текущий этап добавления Ozon](https://linear.app/mktvision/document/marketvision-dobavlenie-ozon-tekushij-etap-arhitektury-b24baee11e0d);
- [целевая архитектура и план распила](https://linear.app/mktvision/document/marketvision-celevaya-arhitektura-i-plan-raspila-na-budushee-f429b301e11a).

### Текущий этап

Сейчас в MarketVision есть Telegram-бот и ядро `core`. Ozon вынесен в этот
отдельный сервис уже на старте:

- `ozon-service` хранит raw-данные Ozon — магазины, участников магазинов и
  номенклатуру — и содержит клиент Ozon Seller API;
- расчёты Ozon-отчётов временно выполняются в ядре через отдельную Ozon-ручку;
- `ozon-service` достаёт raw из своей базы, формирует узкий DTO для конкретного
  отчёта и передаёт его ядру;
- ядро возвращает готовый расчёт, после чего `ozon-service` отдаёт результат
  клиенту.

Транспорт между сервисами закладывается как gRPC + protobuf. DTO должны быть
узкими и содержать только поля, необходимые конкретной формуле; полное raw-
хранение остаётся в `ozon-service` для будущих типов отчётов.

### Целевая архитектура

Планируемое разделение идёт по источнику данных и назначению:

1. `ozon-service` — raw-данные и доменная логика Ozon;
2. `wb-service` — raw-данные и доменная логика Wildberries;
3. `users-service` — пользователи, авторизация и общая связь пользователь ↔
   магазин;
4. `report-service` — stateless-калькулятор, не знающий о Ozon/WB API и
   возвращающий единый формат результата для отчётов разных маркетплейсов;
5. `tg-bot` — клиентский слой без изменений в этой части архитектуры.

В целевом потоке клиент обращается к marketplace-сервису, а тот оркестрирует
получение raw-данных и вызов `report-service`:

```text
client ──► ozon-service ──► report-service ──► ozon-service ──► client
              │                                    ▲
              └── raw из своей БД → узкий DTO ──────┘
```

Асинхронный request-reply через Kafka рассматривается только при доказанной
необходимости для тяжёлых расчётов или пиковых нагрузок; заранее оптимизировать
транспорт не требуется.

## Запуск

Требуется Go 1.24 или новее:

```bash
go run ./cmd/app
```

По умолчанию HTTP-сервер слушает `:8080`. Адрес можно изменить переменной
окружения `HTTP_ADDR`, например `HTTP_ADDR=:9090 go run ./cmd/app`.

Проверка доступности:

```bash
curl http://localhost:8080/healthz
```

Сейчас HTTP-сервер является заглушкой: он предоставляет endpoint `/healthz` и
корректно завершается по `SIGINT` или `SIGTERM`. gRPC-контракт будет добавлен
вместе с первой межсервисной операцией и соответствующей OpenSpec-документацией.

## Структура

- `cmd/` — точки входа приложения;
- `internal/` — весь код сервиса, включая приложение, адаптеры, доменные
  пакеты и внутренние переиспользуемые пакеты;
- `openspec/` — предложения, дизайн и задачи изменений;
- `AGENTS.md` — правила работы с репозиторием и окружениями.
