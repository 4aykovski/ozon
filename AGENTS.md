# AGENTS.md

## Назначение репозитория

Это Go-сервис `ozon-service` для Ozon-домена MarketVision. Он владеет
интеграцией с Ozon Seller API и полным raw-хранением данных Ozon. Расчёт
отчётов выполняется ядром на текущем этапе и должен быть выделен в отдельный
`report-service` в целевой архитектуре.

## Обязательные правила работы

1. Если запрашивается задача, требование или архитектурное решение, сначала
   найти соответствующую задачу и документы в Linear команды `Development`.
   Идентификатор задачи (например, `DEV-20`) использовать как основной ключ
   поиска. Локальные предположения не заменяют актуальное описание в Linear.
2. Любое изменение должно сопровождаться OpenSpec-документацией в
   `openspec/changes/<change-name>/`: как минимум `proposal.md`, `design.md` и
   `tasks.md`. Реализация выполняется только после описания решения в OpenSpec;
   после завершения нужно обновить задачи и синхронизировать затронутые спеки.
3. Статус задачи в Linear нужно поддерживать в соответствии с фактическим
   этапом работы. При начале реализации переводить задачу из `Todo` в `In
   Progress`, после завершения разработки и подготовки результата к проверке —
   в `In Review`, после принятия результата — в `Done`. Если работа остановлена
   из-за внешнего блокера, использовать `Blocked` и описать причину в задаче.
4. Если работа начинается из ветки `main`, сначала создать и переключиться на
   отдельную ветку задачи. Не вносить рабочие изменения непосредственно в
   `main`. Имя ветки должно содержать идентификатор задачи, если он есть.
5. Если задача затрагивает код, но для неё нет задачи в Linear, сначала создать
   задачу в Linear и привязать работу к её идентификатору. После создания
   проверить описание и только затем начинать реализацию.
6. Любые изменения в production и staging — деплой, конфигурация, миграции,
   данные и инфраструктура — допускаются только после явного approval
   пользователя/ответственного. Наличие `full access` это правило не отменяет.
   Без approval остановиться и запросить его; не считать доступ разрешением.
7. Не коммитить секреты, токены, `.env`, дампы и реальные пользовательские
   данные. Не выполнять необратительные действия без подтверждения точного
   объекта и назначения.

## Архитектурные ориентиры

- Текущий поток: `client → ozon-service → core (Ozon endpoint) → ozon-service →
  client`.
- Будущий поток: `client → marketplace-service → report-service →
  marketplace-service → client`.
- Межсервисный транспорт — gRPC + protobuf; контракты должны использовать
  узкие DTO под конкретный отчёт.
- Полные raw-данные остаются в marketplace-сервисе; `report-service` не знает
  о маркетплейсах и не хранит их данные постоянно.
- Пользователи, авторизация и общая связь пользователь ↔ магазин относятся к
  будущему `users-service`, а не к Ozon-специфичному коду.
- Код приложения размещается в `internal/`; точки входа — в `cmd/`.

## Локальная разработка

```bash
go run ./cmd/app
go test ./...
go vet ./...
```

HTTP-заглушка слушает `:8080`, адрес задаётся через `HTTP_ADDR`. Endpoint
`GET /healthz` используется для проверки доступности.

Перед изменением публичного или межсервисного контракта сначала обновить
OpenSpec, затем код и тесты. Сгенерированный код в будущем не редактировать
вручную: менять исходную спецификацию и запускать генератор, описанный в
OpenSpec.
